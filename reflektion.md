## KK2, an LLM based data analysis API

KK2, as constructed, is an API built around the Python transformers library. Using FastAPI for the API framework, and Pandas for data analysis. The purpose being to allow the user, user and end-user being used interchangeably in this case, to upload a CSV dataset, and then give them the ability to ask the LLM questions about the dataset in plain language.

The KK2 API was constructed with the purpose of adhering to pythonic design philosophies, making use of pythons built in functions and features to solve problems, rather than building solutions from the ground up, hopefully creating more elegant solutions in the process.

A library which lends itself to this design philosophy is the Pydantic data validation library. This library was heavily utilized in constructing the LLM logic flow. Using Pydantic’s Basemodel to construct models with type validation, which could then be extended with the custom class Runnable.
In this Runnable class we can enforce which functions should be implemented in any class which extends it, similar to an interface, while also making use of operator overloading, redefining what happens when an operator is used on the class. By making use of this we can override operators such as the OR operator, to construct a chain from the API-call, essentially creating a sequence of classes to be called, while defining how the out and inputs should be handled between them.

While all the logic of these Runnables can be handled through traditional classes and functions, whether that be type enforcement, or operator overloading, the benefit of constructing a Runnable chain using Pydantic’s Basemodel is that it allows us to put a lot of the logic of how they should behave away from where new code is being implemented, while enforcing consistent behaviour. This is in contrast to how a typical programming workflow would look, where one would typically call the separate functions, and save their outputs, before calling the next function in the same non-chain sequence of functions needed to be called. Or as was the case of the KK2 API before refactoring, doing a lot of manual appending in the API class before calling the LLM function with the constructed query. While personally I did clash on occasion with this design philosophy, it is certainly a useful tool, allowing the programmer to pre-define behaviors, and create very simple calls, especially if there is need to create different chains of the same classes.


As with any project with a limited scope the KK2 API is constructed with some limitations, while also keeping a more restricted use-case in mind. Meaning that while the project is designed to be scalable, the final iteration of the API was designed such that the user is able to access the entire history of any previous conversation, with no purpose-built restrictions in place.

While this was designed to limit the scope of the API, as any solutions, such as user management, databases, and any form of locking down of access to the APIs memory was beyond the scope of the project specifications. Discussion of the risks and the required steps to mitigate this risk is certainly worthwhile.

As has been touched upon, if the API was to be scaled up in scope such that it were to deployed on a wider scale, to allow for users, other than the person deploying it locally, to access it, we would be running into a few different issues. Foremost of these would be the fact that the LLM always has access to the entire conversation history, each time it is prompted. From a legal and security standpoint, this means that we would potentially be exposing sensitive data between users, which, although local laws may still be catching up with specifics about AI training data in some places, would almost definitely put the publisher of the API at risk because of various data protection laws, such as those required by GDPR. From a practical standpoint this is also a rather significant limitation, as multiple users would all be sharing one conversation history, not just between one another, but also between sessions, meaning that answers would both take longer to process, and quickly become incoherent.

Of course, this limitation is also present in other parts of the API, other than the LLM implementation, actions such as uploading a CSV file, and its data, are built around the assumption that only one CSV will be analyzed at a time. This means that the CSV file could be overwrittens before a user could ask their questions about the dataset, and would also mean that any sensitive data in the CSV would be exposed to all users.

To mitigate these risks, would also necessitate a re-design from the ground up of the APIs implementation, storing CSV data per user, or access session. While also constructing some form of database solution to handle chat history between specific users and the LLM. Also allowing us to store the data in the event of a crash of the backend, and the ability to clear history in accordance to GDPR data expiration laws, given that we also store a timestamp with the history of course.

Some security risks may also appear due to specific implementation details, such as how we handle CSV file uploads, while the API does perform some strict sanity checks, such as limiting the size of the file uploaded, and making sure that the file uploaded is, in fact, a CSV file, it may still leave some things unchecked, such as the specific value in the csv fields, even forgoing any typechecks in this case, which could lead to a potential crash if these fields were to be corrupted in an otherwise legitimate CSV file. This could also be used as a potential attack vector for something like prompt injection, although it should be noted that the question given through the ask/ai endpoint is a much more likely vector for this, as we, indeed, do not perform any form of sanity checks on the questions a user is able to ask, other than casting it as a string.

Indeed, the API could not necessarily be said to be insecure, provided the limited, intended, scope is followed, namely 1 user running it locally, as any potential security and legal risks are limited in this case, issues such as prompt injection for a text based LLM which has no file access being rather limited, provided that Python’s transformers library is implemented in a secure manner, that is. Injections such as massive strings, or non-word prompts, also being something which could be mitigated by enforcing a much more limited question structure or by discarding non-intended characters from the prompt before feeding it to the LLM. Meaning also that security measures, which were implemented in case of a larger scope, such as handling environment variables, which ought to be used for LLM API keys, in case of a non-local LLM implementation, a sensible solution for a larger project, or database key, which would also be sensible were the project to necessitate a proper database, also a good assumption in a scaled up scope, goes, in part, unused. Conclusively, the API would indeed need a lot of refactoring not to be considered greatly insecure were it to be deployed at any scale.


Aside from some of the more apparent limitations, such as lacking ways to clear the prompt memory without restarting the API, when the API is used in the limited scope it is designed for, the largest technical hurdle ended up being the limitations of the SmolLM model the API is designed around, or more specifically the 135M param model, the product of a team of computer science researchers, to be able to run with only 135 million parameters, meaning the number of weights which are trained. While this does make it light weight enough to be able to run locally on a laptop, it does come at a cost to the LLMs abilities, when compared to a much larger model, meaning that the AI is more limited in usecase, and in most cases also less useful than a large model.

In the case of the KK2 API, this did indeed act as a severe limitation, preventing the LLM from giving coherent answers about the CSV data, or about prior conversations. The way this was mitigated was to switch to a newer model by the same team, SmolLM2, which was overtrained on 11 million tokens of data, discussed further in the research paper published by the same team. While this model gave drastically better answers, able to mostly answer questions about earlier conversations, and give concrete answers about the information given to it about the CSV data, it still does in large part hallucinate a lot of answers, and its abilities are obviously constrained as compared to larger models with more parameters. Having a smaller model also means that any bias from its training data is more likely to appear in its responses. One way this could be seen was on the occasions it gave fictitious answers about the CSV data, often attempting to give answers it would expect about rather than what was there. A real example being, that when asked about the mean of a field called “sleep hours” it would often answer with a very reasonable number which a person on average would sleep, rather than what was in the data it was provided.

While the limitations are apparent, the capabilities are indeed impressive, and it has been a surprise to see how quick it is to get a fairly capable model up and running locally on an 8 year old laptop, lending itself to the fast iterative process of the Python language.
